## 2. Выполнение задания №1: анализ исходного проекта

Перед изменением кода был изучен исходный Django-проект Investing Demo.
Исходное приложение предназначено для хранения каталога акций, просмотра
рыночных инструментов, CRUD-операций и получения текущих цен через Tinkoff
Invest API.

Исходный технологический стек:

- Python и Django;
- PostgreSQL;
- Django REST Framework;
- `django-filter`;
- Celery;
- Redis;
- Tinkoff Invest SDK;
- Plotly;
- Bootstrap 3 и crispy-forms.

Основные компоненты:

- `config/` — настройки Django, маршруты, WSGI/ASGI и Celery;
- `dashboard/` — модель `Share`, HTML views, REST API, формы, шаблоны,
  интеграция с Tinkoff и фоновые задачи;
- `user/` — регистрация и аутентификация пользователей;
- `dashboard/models.py` — исходная сущность акции;
- `dashboard/tasks.py` — периодическое обновление цен;
- `dashboard/api/v1/` — REST API для работы с акциями.

В исходной версии модель `Share` содержала FIGI, ISIN, название, тикер,
валюту, UID, последнюю цену, признак изменения тренда и время обновления.
Пользовательские наблюдения, уведомления, портфели и история цен отсутствовали.

Результаты анализа сохранены в сравнительном и проектном материале
`ANALYSIS.md`, а технические изменения перечислены ниже.

## 3. Выполнение задания №2: восстановление требований

По исходному коду были восстановлены следующие фактические требования:

1. Приложение отображает список акций, отсортированный по названию.
2. Пользователь может открыть страницу отдельной акции.
3. На странице акции отображается график рыночных данных.
4. Аутентифицированный пользователь может создать акцию.
5. Аутентифицированный пользователь может изменить акцию.
6. Аутентифицированный пользователь может удалить акцию.
7. REST API поддерживает получение списка и отдельной акции.
8. REST API поддерживает создание, изменение и удаление акции.
9. API поддерживает фильтрацию по названию и тикеру.
10. API поддерживает поиск и сортировку.
11. Celery-задача обновляет текущие цены акций.
12. При обновлении цены вычисляется направление изменения.
13. Команда `add_shares` загружает первоначальный набор акций.
14. Приложение предоставляет регистрацию и аутентификацию пользователей.

Дефекты и ограничения исходной версии не включались в список требований. Отдельно
были отмечены жёсткая конфигурация PostgreSQL, пустые секреты, отсутствие
локального fallback, прямой вызов `get()` для деталей акции и недостаточная
обработка ошибок внешнего API.

## 4. Выполнение задания №3: модернизация и исправления

В этой ветке были выполнены следующие изменения:

### Конфигурация и запуск

- `SECRET_KEY` переведён на чтение из переменной окружения с локальным
  значением по умолчанию.
- `DEBUG` и `ALLOWED_HOSTS` настраиваются через переменные окружения.
- PostgreSQL настраивается через `POSTGRES_HOST`, `POSTGRES_DB`,
  `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_PORT`.
- Для локальной проверки добавлен SQLite fallback, если `POSTGRES_HOST` не
  задан.
- `CELERY_BROKER_URL` можно задать через окружение.
- Tinkoff-токен читается из `TINKOFF_TOKEN`.

### Обработка ошибок и интеграции

- Tinkoff SDK импортируется внутри функций интеграции, поэтому обычные команды
  Django не падают из-за отсутствующего внешнего клиента.
- При отсутствии Tinkoff-токена выбрасывается явная ошибка с понятным
  сообщением.
- Пустой ответ Tinkoff API обрабатывается явно, без небезопасного вызова
  `pop()` на пустом списке.
- Страница несуществующей акции возвращает стандартный HTTP 404 через
  `get_object_or_404`.
- Существующее логирование ошибок Celery сохранено.

### Зависимости и совместимость

Исходные зафиксированные зависимости не устанавливались в текущем окружении
Python 3.15: установка остановилась на старой версии `grpcio` и устаревшей
цепочке сборки. Поэтому `requirements.txt` был переведён на совместимые
диапазоны версий для Django, Celery, DRF, Redis, Plotly и инструментов
форматирования. Проблема исходного окружения зафиксирована, а не скрыта.

## 5. Выполнение задания №4: персональный мониторинг акций

В качестве новой функциональности выбран персональный мониторинг акций.

Добавлены модели:

- `PriceAlert` — пользователь, акция, целевая цена, направление, активность и
  время срабатывания;
- `PriceAlertNotification` — зафиксированное уведомление о срабатывании.

Реализовано:

1. Авторизованный пользователь создаёт условие наблюдения.
2. Условие содержит акцию и целевую цену.
3. Поддерживаются направления `above` и `below`.
4. API возвращает только наблюдения текущего пользователя.
5. API не позволяет пользователю читать чужие уведомления.
6. Celery-процесс проверяет условия после обновления цены акции.
7. При достижении цены создаётся уведомление.
8. Повторная проверка уже сработавшего условия не создаёт дубликат.
9. Добавлены endpoints:
   - `/api/v1/price-alerts/`;
   - `/api/v1/price-alert-notifications/`.
10. Добавлена миграция
    `dashboard/migrations/0008_pricealert_pricealertnotification.py`.
11. Добавлены тесты доступа и дедупликации уведомлений.

Остальные направления из задания №4 — виртуальный портфель, история цен и
симулятор стратегий — в этой ветке не реализовывались. Выбран один законченный
вариант новой функциональности, чтобы сохранить тестируемость и не добавлять
несвязанные незавершённые модули.

## 8. Ограничения и итог

Основное ограничение — отсутствие исходного совместимого окружения для старых
зафиксированных зависимостей на Python 3.15. Для проверки использовался
совместимый набор пакетов, а требования к зависимостям были обновлены.

Итог Copilot-ветки: исходная функциональность CRUD/API сохранена, приложение
проходит проверки Django и запускается локально, а персональный мониторинг
акций добавлен с миграцией, API, Celery-проверкой и тестами.
